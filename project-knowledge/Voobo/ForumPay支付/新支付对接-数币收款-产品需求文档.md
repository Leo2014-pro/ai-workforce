## 1. 需求背景与目标

### 1.1 为什么做 [建议]
平台现有多为法币收单，缺少**数币（加密货币）收款**能力。数币用户无法完成会员 / AI 代币等付费。本次接入 **ForumPay 数币收款**打通该能力，并将其并入**统一渠道管理**体系，保证多币种、多支付类型、多渠道在后台可统一配置与查看。

### 1.2 目标（做什么）
- 接通 ForumPay 数币收款。
- 后台**统一渠道管理**：数币、法币渠道同一套管理，配置各渠道的**启用状态、支持币种、支持支付类型**，并通过“渠道”字段区分。
- 支付订单列表：识别并展示该笔支付归属 **充值 / 会员购买 / AI 代币购买**；新增 **“后台备注”** 字段供运营标注（尤其线下处理类订单），**不对用户展示**。
- 前端：提供**直观的数币收银台**（步骤化引导、金额/地址/到账状态清晰）。

### 1.3 非目标（本轮版本）
- **不做**“先充值到平台账户余额再消费”的完整链路；本轮仅接通数币支付。
- **不做**退款操作、不做少付/多付自动接受（异常走线下）。
- **不做**账户余额自动入账逻辑（充值=余额充值，余额“加钱”机制后续单独定）。
- 不自建加密钱包/链上结算；不展示网络手续费拆分（用户承兑）。
- 渠道不做“新增/删除渠道”能力；KYT 关闭。

### 1.4 成功判断
- 数币/法币可在统一渠道管理中开启、禁用，配置各自币种与支付类型并生效。
- 一笔数币订单从前台发起 → 出码 → 用户到账 → 支付成功回流；后台归属、币种、金额、状态、后台备注可读可查、可对账。
- 数币支付成功后业务到账一次且仅一次。

## 4. 总体流程

```
前端收银台 选“数币支付” → 选币种
    │ 后端调 ForumPay StartPayment（invoice=USD, currency=所选币种）
    ▼
返回 address / qr_img / amount / rate / payment_id
    │ 前端展示：应付金额 + 收款地址/二维码 + 步骤化到账引导 + 倒计时
    ▼
用户链上转币 → ForumPay 确认（达最小确认数）
    │ Webhook + 平台主动 CheckPayment 对账
    ▼
订单置“已支付”→ 成功到账一次（会员开通 / 代币发放 / 余额充值[机制后续单独设计]）
    │
管理后台：统一渠道管理 / 支付订单（归属、币种、金额、状态、后台备注）
```

## 5. 需求模块一：后台 · 统一渠道管理

### 5.1 定位 [已确认]
渠道管理为 **数币 + 法币统一的渠道管理**。数币渠道为系统固定存在，**不做新增/删除**；法币渠道按其现有接入管理，共同在一套列表/页面中维护。每条渠道通过 **“渠道”字段** 区分（数币 / 法币 / 具体网关）。

### 5.2 渠道列表字段
| 展示项 | 说明 |
|---|---|
| 渠道 | 渠道字段：区分该条是**数币（ForumPay）**还是**法币（微信/支付宝/银行卡等）** |
| 渠道名称 | 展示名 |
| 支持币种 | 该渠道可收的币种（如数币=BTC/ETH/USDT…；法币=CNY/USD…）**[由渠道配置]** |
| 支持支付类型 | 该渠道可用于哪些业务付费（充值/会员购买/AI代币购买）**[由渠道配置]** |
| 状态 | 开启 / 禁用 |
| 操作 | 配置（进入编辑币种与支付类型） |

> 支付币种、支付类型**均来自渠道配置**，不全局写死；同一币种或支付类型可同时被数币、法币多条渠道支持。**[已确认]**

### 5.3 单渠道配置
| 字段 | 说明 |
|---|---|
| 渠道（标识） | 固定，不可改（数币=ForumPay / 法币=对应网关） |
| 启用状态 | 开启/禁用；禁用后前端不再展示该渠道 |
| 支持币种 | 多选；仅勾选币种可被选择 |
| 支持支付类型 | 多选（充值/会员购买/AI代币购买）；勾选后该渠道仅用于这些业务 |

> 明确不在渠道页配置：API Key、回调地址、pos_id、结算账户、费率等，维护于网关侧/平台隐藏配置。**[已确认]**
> 运营统计（收款笔数/金额）不在渠道页展示，独立统计页承接。**[已确认]**

### 5.4 交互与校验
- 币种、支付类型从系统/网关既有集合勾选，不开放自由录入。**[建议]**
- 币种与支付类型按“各自多选”平级配置，暂不做矩阵化细分；后续有需要再扩展。**[已确认]**
- 保存即时生效；生效/缓存延迟与现有渠道配置一致。**[建议]**

## 7. 订单状态机

> 网关侧状态经 `state`/`confirmed`/`cancelled` + 确认数表达；平台侧状态为本需求定义，状态枚举与现有系统的字段映射由技术对齐后落地。**[已确认：状态划分可用]**

| 状态 | 含义 | 触发到账 | 前台可见 | 后台处理 |
|---|---|---|---|---|
| 待支付（waiting） | 已出码，等待转币 | 否 | 展示地址/二维码、倒计时 | 可取消 |
| 确认中（confirming） | 链上已见交易、未达最小确认数 | 否 | 提示确认中 | 只读 |
| 已支付（confirmed） | 达最小确认数 | 是（一次） | 到账回执 | 可查可对账 |
| 已失效（expired） | 超时/取消 | 否 | 提示失效可重下 | 只读 |
| 差异（difference） | 少付/多付，不自动接受 | 否 | 引导联系客服 | **线下处理 + 后台备注** |

约束：最终态为已支付 / 已失效 / 差异之一，不重复触发到账；回调与主动查询需幂等。
**[已确认]**：确认延迟（链上未达确认）系统不自动强补偿，超时/异常统一**线下客服处理**并在后台备注记录。

## 8. 需求模块三：前端 · 数币收银台（直观版）

> 交互目标：让用户一眼看清 **付多少（币种/金额/汇率）、付到哪（地址/二维码）、付了没（到账状态）**，并给出明确下一步操作。本模块配套《数币收银台高保真原型》HTML，按下列状态与交互实现。

### 8.1 收银台页面结构（按主次信息层级）
1. **顶部摘要区（最关键信息最先）**
   - 业务名与订单信息（购买会员 / AI 代币、数量、订单号）。
   - **应付金额大字号**：USD 金额为主，切换币种后联动显示对应数币金额。
2. **币种选择区**
   - 展示渠道启用的币种（如 BTC/ETH/USDT），默认给推荐（如对应 USD 稳定币）；选中即时刷新二维码与应付金额。
3. **收款信息区（地址 + 二维码并列，避免来回滚动）**
   - 二维码居中放大（`qr_img`）。
   - 收款地址 + “复制”按钮（复制后有明确 toast 反馈）。
   - 币种/网络提示（若网关返回 `notices`，用醒目光标显示，如“请确认 USDT 走 ERC20 网络”）。
4. **到账引导区（步骤化，直观展示“进行到哪一步”）**
   - ① 完成转账 → ② 等待确认 → ③ 到账成功。
   - 当前步骤高亮；未达确认前步骤②带进度/提示“确认中，通常 X~Y 分钟”。
5. **金额与时效提示**
   - 提示“请按页面金额转账，勿多转/少转”，避免差额订单。
   - 报价/订单**倒计时**，超时整页转“已失效”态并给出“重新支付”按钮（不自动锁价刷新）。
6. **操作区**
   - 主按钮“我已转账，查询到账”；次操作“取消订单”。
   - 到账成功后自动跳转业务回执（会员已开通 / 代币已到账）。

### 8.2 关键状态（前端可见）
| 状态 | 页面表现 |
|---|---|
| 待支付 | 摘要+收款码+步骤①②高亮，倒计时中 |
| 确认中 | 步骤②高亮并提示确认中，二维码区收缩 |
| 已支付 | 成功态，步骤③完成，展示回执/跳转按钮 |
| 已失效 | 全屏提示“订单已失效”，附“重新支付” |
| 差异/异常 | 提示“到账金额与应付不一致”，引导联系客服（客服侧经后台备注记录处理） |

### 8.3 回流（成功到账）
- **[已确认]** 现有系统仅有法币支付，**数币成功到账逻辑需新建**，无法复用现有法币到账链路。
- 幂等：一笔订单仅到账一次；回调与主动查询不重复发放。
- 到账失败需重试与后台可处理入口；余额充值场景到账=调用后续“余额入账”机制（本轮仅预留调用点）。**[建议]**

## 10. 验收标准

1. 统一渠道管理可查看并管理**数币与法币**渠道，每渠道以“渠道”字段区分；可开启/禁用并配置各自**支持币种与支持支付类型**；禁用后前端不再展示该渠道。
2. 前端数币收银台直观呈现：应付金额（USD+数币联动）、收款地址、二维码、步骤化到账引导、倒计时；不出现手续费拆分字段。
3. 数币支付成功订单，后台归属列正确显示“充值 / 会员购买 / AI 代币购买”之一，币种、金额、汇率、状态、单号、**后台备注**可读可筛；后台备注不出现在任何面向用户的信息中。
4. 支付成功到账一次且仅一次，重复回调不重复到账。
5. 订单状态流转：待支付→确认中→已支付 / 已失效 / 差异，前后台一致；差异/延迟/需退款类订单可添加后台备注并线下处理。
6. 订单超时后收银台整页提示“已失效”并可重新发起。
7. 可通过主动查询补齐未收到回调订单，终态与网关一致。

## 11. 风险提示

- **[风险]** 链上确认延迟/卡单可能引发用户客诉；已明确超时与延迟统一**线下客服处理**，需在订单上可定位并记录后台备注。
- **[风险]** 少付/多付不自动接受，会产生差异订单线下人工处理，需后台备注与定位能力，避免账实不清。
- **[风险]** 数币成功到账逻辑无法复用现有法币链路，需独立建设，强化幂等与补偿，避免重复发放/漏发。
- **[风险]** 充值归属对应的余额入账机制未定，前端可先行接通支付与“支付成功”节点，但“充值到账”需预留调用点，避免上线后补窟窿。
- **[风险]** 汇率波动可能造成下单与结算差异；页面以“按所示金额转账 + 超时失效”规避锁价争议。
- **[风险]** 数币涉及合规（链上可追溯、限额）；本轮 KYT 关闭、不做退款，上线前需合规侧评估。
