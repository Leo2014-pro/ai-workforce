## 1. 需求背景与目标

### 1.1 为什么做 [已确认·项目知识]
钱包是「订阅付费 + 邀请奖励 + 充值」三条商业链路的底层依赖，为全项目最高优先级欠账（P0）。订阅页面是「AI 聊天 + AI 交易 + 会员付费」商业闭环的核心变现入口。本需求输出钱包与订阅的完整前端及后台管理能力，解除商业闭环阻塞。

### 1.2 目标
1. 用户前端**钱包页面**：展示美金、AI 代币、令牌三个资产余额，以及钱包流水（充值、营销奖励、会员购买、令牌购买、赠送礼物）。
2. 用户前端**订阅页面**：订阅会员、购买令牌、赠送（支持选择多个受赠人；会员与令牌均可赠送）。
3. 管理后台**会员资产页面**：展示会员三个资产的余额与记录，支持资产流水查询与资产调整（调整需谷歌验证）。
4. 管理后台**赠送记录页面**：展示礼物赠送记录（支付用户、赠送用户、会员数量、令牌数量）。

### 1.3 非目标（本版不做）
- **不做订阅规则**：套餐定义、价格、权益明细、会员有效期规则等，后续单独定稿。本需求只做订阅页面的信息架构与交易流程。
- **不做 AI 代币与令牌的具体消耗流水类型**（用户说明：AI 代币以及令牌流水待定），流水模型预留扩展。
- **不做营销奖励的发放规则**（邀请返佣规则后续定稿），流水类型预留「营销奖励」。
- **不做充值收银台**（ForumPay 数币收款已单独定稿），本需求只承接充值成功后的入账与流水。

### 1.4 成功判断
- 用户可在钱包页看到三个资产的准确余额，流水可按类型/资产/时间查询，且与实际发生业务一一对应。
- 用户可在订阅页完成：订阅会员、购买令牌、向多人赠送会员/令牌；支付成功后各受赠人资产/会员状态准确到账，一次且仅一次。
- 后台可查询任意用户的资产余额与流水，可经谷歌验证后调整资产并留下可审计记录；赠送记录可查。

## 2. 角色与场景

| 角色 | 场景 | 诉求 |
|---|---|---|
| 终端用户（H5） | 查看自己的资产与流水 | 余额准确、流水清晰（每笔钱/币来去可查） |
| 终端用户（H5） | 订阅会员、购买令牌 | 流程直观，支付成功后即时到账 |
| 终端用户（H5） | 向朋友赠送会员/令牌（可多选） | 选人方便、赠送后对方到账、自己有记录可查 |
| 平台运营/财务（后台） | 查询用户资产、排查流水 | 余额与流水可查可对账 |
| 平台运营/财务（后台） | 修正用户资产（异常补偿等） | 强校验（谷歌验证）、留痕可审计 |
| 平台运营（后台） | 查看赠送记录 | 赠送关系与数量一目了然 |

## 4. 资产与流水模型（本需求的业务底座）

### 4.1 资产方向总览 [建议]

| 资产 | 增加来源 | 减少来源 |
|---|---|---|
| 美金 | 充值入账（**含订阅页直接支付的资金入账**，见 §6.2）、营销奖励、后台调整（调增） | 会员购买（余额扣减）、令牌购买（余额扣减）、赠送支出、后台调整（调减） |
| AI 代币 | 购买（余额扣减美金后发放）、后台调整（调增） | 消耗场景待定、后台调整（调减） |
| 令牌 | 购买（余额扣减美金后发放）、受赠、后台调整（调增） | 消耗/使用场景待定、后台调整（调减） |

> AI 代币当前流水「购买」外无确定类型；令牌流水类型整体待定。流水模型按「资产 × 类型 × 方向」设计，新增类型不需改表结构。[已确认·占位扩展]

### 4.2 用户端钱包流水类型（本期展示）

| 流水类型 | 资产 | 方向 | 触发 | 状态 |
|---|---|---|---|---|
| 充值 | 美金 | + | **所有支付资金先进美金余额**：ForumPay 支付订单置「已支付」后入账（含订阅页直接支付的资金入账） | [已确认] |
| 营销奖励 | 美金 | + | 类型占位；发放规则待定 | [已确认·占位] |
| 会员购买 | 美金 | − | 订阅页购买会员，**从美金余额扣减** | [已确认] |
| 令牌购买 | 美金 − / 令牌 + | 跨资产 | 订阅页购买令牌，美金余额扣减 + 令牌入账（整数）；建议生成两条互相关联的流水（同一订单号） | [已确认] |
| 赠送礼物 | 视赠送内容 | 送出 − / 受赠 + | 赠送成功；送出方与每个受赠方各生成流水 | [已确认] |
| 后台调整 | 任意资产 | ± | 后台资产调整（见 §7.2）；⚠️ **下发口径见下方重点说明** | [已确认] |
| AI 代币流水类型 | AI 代币 | — | 待定 | **[待确认·占位]** |
| 令牌流水类型 | 令牌 | — | 待定 | **[待确认·占位]** |

> ### ⚠️ 重点说明（防止开发遗漏）：「后台调整」的展示口径下发
> 1. **管理后台**：该类流水展示为「**后台调整**」，关联调整单号、操作人、原因，可审计。
> 2. **用户前端（钱包流水）**：同一笔流水**下发到前端时，业务类型统一显示为「**营销奖励**」**，不出现「后台调整」字样，且不下发操作人/原因等后台字段。
> 3. 即：**同一笔数据、两端口径不同**——后台「后台调整」= 前端「营销奖励」。开发实现时必须在接口下发层做类型映射，不允许直接透出后台类型。**[已确认]**

### 4.3 流水统一字段 [建议]
流水ID、用户ID、资产类型（美金/AI代币/令牌）、业务类型、方向（收入/支出）、变动数量、变动后余额、关联单号（支付订单号/赠送记录号/调整单号）、时间、备注（可选）。

## 5. 用户前端 · 钱包页面

### 5.1 页面结构 [建议]
```
钱包页
├─ 资产卡片区：美金 / AI 代币 / 令牌（余额 + 单位）
├─ 流水筛选区：资产类型（全部/美金/AI代币/令牌）× 业务类型（全部/充值/营销奖励/会员购买/令牌购买/赠送礼物/…）× 时间区间
└─ 流水列表：类型、资产、数量（收入+/支出−，颜色区分）、时间、备注；分页
```

### 5.2 规则
1. 余额展示三个资产当前余额；数据口径为钱包余额实时值。[已确认]
2. 流水默认按时间倒序，支持分页。[建议]
3. 数量展示：收入「+」、支出「−」，颜色区分（收入绿/支出红或按设计稿，与订单中心 Buy/Sell 颜色约定一并对齐）。[建议]
4. AI 代币、令牌的专项流水类型定稿后，在此筛选器中扩展，不影响页面结构。[待确认·占位]
5. 空状态：无流水时展示引导（如「去充值」「去订阅」入口）。[建议]

### 5.3 异常
- 流水加载失败 → 重试入口；余额与流水不一致属异常，不允许出现（任何余额变动必有流水）。[建议]

## 6. 用户前端 · 订阅页面

### 6.1 页面结构 [建议]
```
订阅页
├─ 订阅会员区：会员套餐展示（套餐名/价格/权益占位，规则后续定稿）→「订阅」
├─ 购买令牌区：令牌商品展示（数量/价格占位）→「购买」
└─ 赠送区：「赠送礼物」→ 赠送流程（见 6.3）
```

> 套餐与令牌商品的具体内容、价格**不含在本需求**，由后续订阅规则定稿；本需求保证页面信息架构与交易流程就绪，内容位可配置填充。[已确认]

### 6.2 订阅会员 / 购买令牌（交易流程）[已确认]
**资金路径铁律：所有支付资金一律先进入美金余额，再从余额扣减完成购买。订阅页同时支持直接拉起支付，支付成功后资金入余额并自动完成购买扣减，对用户表现为一条流程。**

```
路径 A（余额充足，余额支付）：
选择套餐/令牌商品 → 确认订单 → 从美金余额扣减 → 到账（会员开通/延长 或 令牌入账）→ 生成「会员购买/令牌购买」流水

路径 B（订阅页直接支付）：
选择套餐/令牌商品 → 确认订单 → 拉起收银台（复用 ForumPay 数币收款流程；法币渠道后续经统一渠道管理并入）
→ 支付成功（订单置「已支付」）→ 资金入美金余额（生成「充值」流水）
→ 系统自动从余额扣减并到账（生成「会员购买/令牌购买」流水）→ 页面状态刷新
```
> 说明：
> 1. 两种路径下「会员购买/令牌购买」流水的触发源一致——均为**美金余额扣减**；区别仅在于路径 B 在扣减前多一步支付入账。[已确认]
> 2. 支付订单业务归属扩展为四类：**充值 / 会员购买 / AI 代币购买 / 令牌购买**。[已确认·归档时同步 ForumPay 口径]
> 3. 路径 B 中若支付成功但自动扣减/到账失败（如系统异常），资金保留在余额，不丢失；购买状态由后台差异处理。[建议]
> 4. 余额不足且用户选择余额支付时 → 引导走路径 B 直接支付。[建议]

### 6.3 赠送流程 [已确认·能力] / [建议·细则]
```
「赠送礼物」→ 选择赠送内容（会员 / 令牌，均可赠送）
→ 选择受赠人（支持多选）
→ 确认（展示赠送内容 × 受赠人数 → 应付金额）
→ 支付成功 → 各受赠人逐一到账 → 生成赠送记录 + 双方流水
```
规则：
1. **受赠人多选**：支持选择多人。[已确认] 选择方式：搜索用户（邮箱/用户ID）后加入列表。[建议]
2. **赠送内容**：会员与令牌均可赠送，且**支持会员 + 令牌组合赠送**（一次赠送中可同时包含会员份数与令牌数量）。[已确认]
3. 受赠人必须为平台**有效注册用户**（未注销）；提交前逐一校验，校验失败即时提示。[建议]
4. 赠送遵循 §6.2 资金路径：支付方资金先进美金余额，再从余额扣减完成赠送；受赠方到账。[已确认]
5. **记录粒度**：一次赠送多人时，**赠送记录按「每受赠人一条」生成；对应的支付订单只有一条，与赠送记录一对多关联**。[已确认]
6. 部分到账处理：扣减成功后逐人到账，单人到账失败不回滚整体扣减，失败项由后台差异处理。[建议]
7. 用户可在钱包流水（赠送礼物）查看自己的送出/受赠记录；后台可在赠送记录页查看（见 §8）。[已确认]

### 6.4 异常
- 支付失败/超时 → 沿用 ForumPay 状态机（待支付→确认中→已支付/已失效/差异），不产生任何资产变动。[已确认·复用]
- 受赠人注销/不存在 → 提交前拦截。[建议]
- 到账幂等：同一支付订单的到账动作一次且仅一次。[已确认·复用]

## 7. 管理后台 · 会员资产页面（替代原「钱包资产」预留表 [已确认]）

### 7.1 会员资产列表
| 展示项 | 说明 |
|---|---|
| 用户ID / 邮箱（脱敏） | 对齐用户列表口径 [建议] |
| 美金余额 / AI代币余额 / 令牌余额 | 三个资产当前余额 [已确认] |
| 会员状态 | 是否会员/有效期 [建议] |
| 用户状态 | 正常/冻结/已注销 [建议] |
| 操作 | 查看流水、调整资产 |

**查询条件 [建议]**：用户ID（精确）、邮箱（模糊）、资产类型、注册/时间区间；导出能力对齐现有后台规范（≤1 万条）。

### 7.2 资产流水查询
- 筛选：用户、资产类型、业务类型、时间区间（默认近 7 天、最大 90 天，对齐交易记录口径）。[建议]
- 字段：见 §4.3 流水统一字段；**只读不可改删**。[建议]

### 7.3 资产调整（核心敏感操作）
**流程 [已确认·谷歌验证] / [建议·细则]**
```
选择用户 → 选择资产（美金/AI代币/令牌）→ 填写调整数量（+/-）+ 调整原因（必填）
→ 谷歌验证 → 二次确认弹窗 → 提交生效
→ 余额更新 + 生成「后台调整」流水（关联调整单号）+ 记操作日志
```
规则：
1. 调整前必须通过**谷歌验证**；操作员未绑定谷歌验证时不可执行调整（提示先绑定）。[已确认·谷歌验证] / 未绑定拦截 [建议]
2. 调整原因**必填**，二次确认，全量记操作日志 —— 对齐用户列表「重置谷歌」敏感操作规范。[已确认·项目规范]
3. 调整后余额不得为负，否则拦截并提示。[建议]
4. 调整记录字段：调整单号、操作人、用户、资产、调整数量（±）、调整前/后余额、原因、谷歌验证通过、时间。[建议]
5. 权限：纳入后台 RBAC 按钮级权限（系统设置口径）。[建议]

### 7.4 异常
- 谷歌验证码错误 → 提示「谷歌验证错误」（对齐登录文案）。[建议]
- 并发调整/支付扣减同一余额 → 余额扣减需保证原子性，不超扣。[移交技术]

## 8. 管理后台 · 赠送记录页面

### 8.1 列表字段 [已确认·核心字段] / [建议·扩展字段]
| 展示项 | 说明 |
|---|---|
| 支付用户 | 付费赠送的用户 [已确认] |
| 赠送用户 | 受赠用户 [已确认]；**一次赠送多人时，每受赠人一行展示 [已确认]** |

## 9. 验收标准

1. **钱包页**：三资产余额准确（AI 代币、令牌为整数）；充值、营销奖励、会员购买、令牌购买、赠送礼物各类流水正确展示、可筛选、可分页；每笔余额变动均有流水。
2. **订阅页**：余额支付与直接支付两条路径均可完成订阅会员与购买令牌；直接支付成功后资金先入余额（充值流水）、再自动扣减到账（购买流水），链路完整；会员状态/令牌余额正确变更且仅变更一次。
3. **赠送**：可多选受赠人，会员与令牌均可赠送且支持组合赠送；资金先进余额再扣减；各受赠人逐一到账；**每受赠人一条赠送记录，整次赠送仅一条支付订单（一对多）**；赠送双方流水与后台赠送记录一致。
4. **后台会员资产页**：三资产余额与流水可查；资产调整必须通过谷歌验证 + 必填原因 + 二次确认方可生效；调整产生流水并记操作日志；负余额被拦截；**「后台调整」流水在后台展示为「后台调整」，下发到用户端显示为「营销奖励」**（见 §4.2 重点说明）。
5. **后台赠送记录页**：字段完整（支付用户、赠送用户、会员数量、令牌数量等），可按条件查询；一人一行、订单一对多关联可验证。
6. **幂等与一致性**：支付到账一次且仅一次；无「有变动无流水」与「有流水无变动」情形。
